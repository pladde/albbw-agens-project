📊 Datenfluss-Architektur

AGENS – Holz & Spielwaren | Auftragsverwaltung (Relationale MariaDB-Datenbank)

🖥️ Frontend

  • React 19 + TypeScript
  • Vite Build-Tool
  • React Router (Navigation)
  • React Bootstrap (UI)
  • Context API (Globaler State: BezirkContext)
  • Port: 5173 (Dev)
⟷

⚙️ Backend

  • Express 5 (Node.js)
  • TypeScript
  • CORS Middleware
  • JSON Body-Parser
  • mysql2 (DB-Client mit Connection-Pool)
  • Port: 3001
⟷

🗄️ Datenbank

  • MariaDB / MySQL
  • Datenbank: agens_service
  • 6 Tabellen
  • Connection-Pool (max. 10)
  • Port: 3306

🔄 Datenfluss: "Auftrag erfassen" (End-to-End)

1
🖥️
Benutzer öffnet die App
Browser lädt React-App über Vite Dev-Server (Port 5173)
main.tsx → App.tsx → BrowserRouter → BezirkProvider
↓
2
🌍
BezirkContext lädt Bezirke
Beim App-Start werden alle Bezirke vom Backend geladen (für das Header-Dropdown)
GET http://localhost:3001/api/bezirk
↓
3
⚙️
Backend verarbeitet GET-Request
Express-Router empfängt Anfrage → bezirkRoutes.ts → SQL-Query
SELECT * FROM bezirk ORDER BY bezirk_id
↓
4
🗄️
Datenbank liefert Bezirke
MariaDB führt Query aus und gibt JSON-Array zurück
[{bezirk_id: 1, name: "Bezirk A", kürzel: "BA"}, ...]
↓
5
🖥️
Frontend speichert Bezirke im Context
BezirkContext speichert Bezirke im globalen State → Header-Dropdown zeigt sie an
useState → setBezirke(data) → Header rendert Dropdown
↓
6
📝
Benutzer wählt Bezirk & klickt "Auftrag erfassen"
Bezirk wird global im Context gesetzt → Navigation zu /dienstleistung/erfassen
setBezirkId(id) → navigate('/dienstleistung/erfassen')
↓
7
📥
Formular lädt Dropdown-Daten
Service-Bereiche, Mitarbeiter und Status werden parallel vom Backend geladen
GET /api/service-bereich + GET /api/mitarbeiter + GET /api/status (Promise.all)
↓
8
✍️
Benutzer füllt Formular aus
Service-Bereich, Mitarbeiter, Status, Titel, Beschreibung, Eingangsdatum, Abschlussdatum
Formular-State in DienstleistungErfassenPage.tsx
↓
9
📤
Frontend sendet POST-Request
Formulardaten werden als JSON an das Backend gesendet (bezirk_id aus Context)
POST http://localhost:3001/api/auftrag
↓
10
⚙️
Backend validiert Fremdschlüssel
auftragRoutes.ts prüft, ob Service-Bereich, Bezirk, Mitarbeiter und Status existieren
SELECT ... FROM service_bereich / bezirk / mitarbeiter / status WHERE id = ?
↓
11
🗄️
Datenbank speichert Auftrag
INSERT mit allen Feldern in die Tabelle auftrag
INSERT INTO auftrag (service_bereich_id, bezirk_id, mitarbeiter_id, status_id, titel, ...) VALUES (?, ?, ?, ?, ?, ...)
↓
12
✅
Backend antwortet mit Erfolg
HTTP 201 Created mit Status "success" und der neuen Auftrags-ID
{status: "success", message: "Auftrag erfolgreich erstellt", data: {auftrag_id: 15, ...}}
↓
13
🎉
Frontend zeigt Bestätigung
Erfolgsmeldung wird angezeigt → nach 1,5s Navigation zur Suchen-Seite
navigate('/dienstleistung/suchen')
↓
14
🔍
Suchen-Seite lädt Aufträge des Bezirks
Nur Aufträge des im Context ausgewählten Bezirks werden geladen (mit JOIN-Namen)
GET http://localhost:3001/api/auftrag/bezirk/:bezirkId
↓
15
✏️
Bearbeiten oder Löschen
Benutzer kann Auftrag bearbeiten (Formular mit Daten befüllt) oder löschen
PUT /api/auftrag/:id | DELETE /api/auftrag/:id

🗄️ Datenbank-Schema (agens_service)

bezirk
🔑 bezirk_id INT PK
name VARCHAR(50)
kürzel VARCHAR(25)
mitarbeiter
🔑 mitarbeiter_id INT PK
vorname VARCHAR(50)
nachname VARCHAR(50)
email VARCHAR(100)
telefon VARCHAR(50)
service_bereich
🔑 service_bereich_id INT PK
name VARCHAR(50)
beschreibung VARCHAR(500)
aktiv TINYINT
status
🔑 status_id INT PK
status ENUM('angenommen','in-bearbeitung','angelehnt','abgeschlossen')
projekt_nummer
🔑 projekt_nummer_id INT PK
projekt_nummer INT
auftrag
🔑 auftrag_id INT PK
🔗 service_bereich_id FK → service_bereich
🔗 bezirk_id FK → bezirk
🔗 mitarbeiter_id FK → mitarbeiter
🔗 status_id FK → status
titel VARCHAR(50)
beschreibung VARCHAR(500)
erstellt_am DATETIME
abgeschlossen_am DATETIME

Beziehungen

  • auftrag (n:1) → service_bereich – Jeder Auftrag gehört zu einem Service-Bereich
  • auftrag (n:1) → bezirk – Jeder Auftrag gehört zu einem Bezirk
  • auftrag (n:1) → mitarbeiter – Jeder Auftrag ist einem Mitarbeiter zugeordnet
  • auftrag (n:1) → status – Jeder Auftrag hat einen Status
