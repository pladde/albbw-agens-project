🖥️ Frontend

  • React 19 + TypeScript
  • Vite Build-Tool
  • React Router (Navigation)
  • React Bootstrap (UI)
  • Context API (Globaler State)
  • Port: 5173 (Dev)

  • TypeScript
  • CORS Middleware

🔄 Datenfluss: "Auftrag erfassen" (End-to-End)

1
🖥️
Benutzer öffnet die App
Browser lädt React-App über Vite Dev-Server (Port 5173)
main.tsx → App.tsx → BrowserRouter → BezirkProvider
↓
2
🌍
BezirkContext lädt Bezirke
Beim App-Start werden alle Bezirke vom Backend geladen (für das Header-Dropdown)
GET http://localhost:3001/api/bezirk
↓
3
⚙️
Backend verarbeitet GET-Request
Express-Router empfängt Anfrage → bezirkRoutes.ts → SQL-Query
SELECT * FROM bezirk ORDER BY bezirk_id
↓
4
🗄️
Datenbank liefert Bezirke
MariaDB führt Query aus und gibt JSON-Array zurück
[{bezirk_id: 1, name: "Bezirk A", kuerzel: "BA"}, ...]
↓
5
🖥️
Frontend speichert Bezirke im Context
BezirkContext speichert Bezirke im globalen State → Header-Dropdown zeigt sie an
useState → setBezirke(data) → Header rendert Dropdown
↓
6
📝
Benutzer klickt "Auftrag erfassen"
Navigation zu /dienstleistung/erfassen → Formular wird angezeigt
DienstleistungErfassenPage.tsx
↓
7
📥
Formular lädt Projekte
Projekt-Dropdown wird mit Daten vom Backend befüllt
GET http://localhost:3001/api/projekt
↓
8
✍️
Benutzer füllt Formular aus
Projekt wählen, Datum, Status, Zusatz-Infos (Key-Value-Paare)
Zusatz-Infos werden als JSON-Objekt aufgebaut
↓
9
📤
Frontend sendet POST-Request
Formulardaten werden als JSON an das Backend gesendet
POST http://localhost:3001/api/auftrag
↓
10
⚙️
Backend validiert und speichert
auftragRoutes.ts prüft Fremdschlüssel (Projekt & Bezirk existieren) und führt INSERT aus
INSERT INTO auftrag (p_id, bez_id, daten) VALUES (?, ?, ?)
↓
11
🗄️
Datenbank speichert Auftrag
Auftrag wird mit JSON-Daten in der "daten"-Spalte gespeichert (Hybrid-Modell)
auftrag_id wird automatisch generiert (AUTO_INCREMENT)
↓
12
✅
Backend antwortet mit Erfolg
HTTP 201 Created mit Status "success" und der neuen Auftrags-ID
{status: "success", message: "Auftrag erfolgreich erstellt", data: {auftrag_id: 15, ...}}
↓
13
🎉
Frontend zeigt Bestätigung
Erfolgsmeldung wird angezeigt → nach 1,5s Navigation zur Suchen-Seite
navigate('/dienstleistung/suchen')

🗄️ Datenbank-Schema (json_hybrid_db)

rolle
🔑 rolle_id INT PK
beschreibung VARCHAR(100)
bezirk
🔑 bezirk_id INT PK
name VARCHAR(50)
kuerzel VARCHAR(50) UNIQUE
person
🔑 person_id INT PK
🔗 r_id FK → rolle
name VARCHAR(50)
vorname VARCHAR(50)
email VARCHAR(100)
telefon VARCHAR(25)
aktiv TINYINT(1)
letzter_login DATETIME
projekt
🔑 projekt_id INT PK
titel VARCHAR(100)
beschreibung TEXT
aktiv TINYINT(1)
erstellt_am DATETIME
projekt_x_person
🔑 x_id INT PK
🔗 projekt_id FK → projekt
🔗 person_id FK → person
auftrag
🔑 auftrag_id INT PK
📦 daten JSON
erstellt_am DATETIME
🔗 p_id FK → projekt
🔗 bez_id FK → bezirk

Beziehungen

  • person (n:1) → rolle – Jede Person hat genau eine Rolle
  • projekt_x_person (n:m) – Verknüpfungstabelle zwischen Projekt und Person
  • auftrag (n:1) → projekt – Jeder Auftrag gehört zu einem Projekt
  • auftrag (n:1) → bezirk – Jeder Auftrag gehört zu einem Bezirk

📦 Hybrid-Modell: SQL + JSON

Strukturierte Spalten (SQL)

auftrag_id: 15      ← Primärschlüssel
p_id: 3          ← Fremdschlüssel → projekt
bez_id: 1         ← Fremdschlüssel → bezirk
erstellt_am: "2026-09-27 18:00:00"

Flexible JSON-Spalte (daten)

{
  "status": "Angenommen",
  "erstellt_am": "2026-09-27",
  "zusatz_infos": [
    { "key": "Lieferdatum",
      "value": "01.10.2026" },
    { "key": "Menge",
      "value": "50 Stück" }
  ]
}
💡 Vorteil: Strukturierte Daten (IDs, Datum) bleiben in SQL-Spalten für schnelle Abfragen & JOINs. Flexible, projektspezifische Zusatzfelder werden als JSON gespeichert – ohne Schema-Änderungen bei neuen Anforderungen.
